# 代码审查（code-review）

对工作区中的代码或变更执行一次系统性的代码审查。适用场景：合入前的 MR/PR 审查、对某个模块或文件的深度检查、安全问题排查。

## 前置条件

- 确定审查范围：`target`（文件、目录或 git 变更集）。若未指定，优先审查当前打开的文件或最近 git diff。
- 若审查范围较大，可派生 `code-reviewer` 子智能体并行分担独立模块（子智能体只读，不会改动文件）。

## 执行步骤

1. **收集范围**：列出目标文件/目录树；若指定了 git 变更，使用 `git_exec` / MCP 工具（`mcp__git__git_diff`、`mcp__git__git_log`）或 `run_command` 获取 `git diff --stat` 与具体 diff。
2. **分面检查**：对每个目标文件，按以下维度逐一检查：
   - **正确性**：逻辑错误、边界条件、空指针/未定义访问、竞态。
   - **健壮性**：异常处理缺失、资源未释放、超时/重试缺失。
   - **安全性**：注入（SQL/命令/XSS/路径穿越）、敏感信息硬编码、权限校验缺失。
   - **性能**：明显复杂度问题、N+1 查询、无必要 I/O。
   - **可维护性**：重复代码、命名、过度复杂、缺乏注释。
3. **逐文件复核**：对高风险发现，阅读上下文代码验证其真实性，避免误报。
4. **输出报告**：按以下 Markdown 结构汇总：

```markdown
## 代码审查报告: <范围>

### 严重问题 (High) — 必须修复
- [文件:行] 问题描述 / 影响 / 修复建议

### 一般问题 (Medium)
- ...

### 建议 (Low)
- ...

### 总结
- 总体评价（1-3 句）+ 修复优先级建议
```

## 规则

- **只读**：不得调用 write_file / edit_file / delete_file 等写工具。
- 每个发现必须给出 `文件:行号` 与可操作的修复建议；无行号定位的发现视为无效。
- 不确定的发现标注「需人工确认」，不要夸大严重程度。
- 报告末尾列出审查过的文件清单。

## 完成判定

输出完整的 Markdown 审查报告，包含分级问题清单、文件行号定位和修复建议。
